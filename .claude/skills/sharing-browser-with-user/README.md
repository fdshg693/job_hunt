# sharing-browser-with-user（メンテナ向け）

「エージェントが可視ブラウザを開き、ログインだけユーザーが手でやる」ための手順書スキル。
実行時の判断は [SKILL.md](SKILL.md) と `references/`。ここは設計意図のみ。

## 何を解決するスキルか

要件は 3 つ:

1. エージェントが **headed** で実ブラウザを立ち上げ、操作をユーザーが目で追える
2. ログイン・MFA・CAPTCHA は**ユーザーが同じウィンドウで手動実行**。エージェントは資格情報を受け取らず、
   認証中の画面も読まない
3. **永続プロファイル**で、サイト側セッションが生きている限りスキル/プロセスをまたいで再ログイン不要

2 は技術的には「読めてしまう」。だから**手順側の明文ルール**として禁止コマンドを名指しで書いている
（SKILL.md「絶対に守ること」と `references/handoff-protocol.md`）。ここを緩めると要件が消える。

## using-playwright-cli との責務分担

| | 担当 |
|---|---|
| [using-playwright-cli](../using-playwright-cli/SKILL.md) | **コマンド仕様の正。** upstream の skill スナップショットをミラーする |
| このスキル | **手順と禁止事項だけ。** フラグ一覧・コマンド一覧は転記しない |

CLI のオプションをここにコピーすると、上流更新で二重管理になって必ず陳腐化する。
`open` / `close` / `list` / `delete-data` / `attach` / `detach` といったコマンド名は手順として出てくるが、
**オプションの網羅表は置かない**というのが線引き。

発火条件の住み分けは `description` に書いてある。ログイン不要のブラウザ操作は
`using-playwright-cli` に流れるよう、「sign-in / MFA / SSO / CAPTCHA / 見せる」を具体語として入れている。

## なぜ `--profile` 固定パスなのか（最重要の設計判断）

`--persistent` の自動生成先は `%LOCALAPPDATA%\ms-playwright\daemon\<daemon-hash>\ud-<session>-<browser>` で、
`<daemon-hash>` が **CLI のインストール実体に紐づく**。`@playwright/cli` を更新するとハッシュが変わり、
旧プロファイルが取り残されて過去のログインが参照できなくなる（0.1.17 → 0.1.19 で実測）。

要件 3（長期保持）と両立しないので、`%LOCALAPPDATA%\claude-browser-profiles\<site>` を明示する方式にした。
リポジトリ外に置くのは、プロファイルに実 Cookie・保存パスワードが入るため（このクローンは公開リポジトリ由来）。

## なぜプロファイル一覧をスクリプトで同梱するのか

手順書だけだと、実行のたびにエージェントが `<site>` 名を新しく決め、パスを組み立て直し、結果として
**使い捨てプロファイルが増える** = 毎回ユーザーに再ログインさせることになる。要件 3（再ログイン不要）が
手順の言い回しだけに依存していた。`scripts/profiles.mjs` はその判断材料（何が既にあり、それが何用か）を
1 コマンドで出すためにある。SKILL.md の Phase 0 が「作る前に必ず見る」を強制する側。

設計上の選択:

- **Node 単体・依存なし。** Git Bash でも PowerShell でも同じ 1 行で動く。bash と ps1 の二重管理を避ける
- **説明はプロファイルの外（`<ROOT>/_meta/<site>.md`）。** 中に置くことは技術的には可能だが、
  「プロファイルディレクトリを読まない」という中核ルールに例外を作りたくない。
  スクリプト自身もディレクトリ名を列挙するだけで、中身は開かない
- **フロントマターは 1 階層の `key: value` だけ。** YAML パーサを持ち込まないため。
  ネストが要るほど複雑になったら、それは設計の見直し時
- **`.env` で置き場を差し替え可能。** `.env` は upstream の `.gitignore` 対象 = リポジトリごとに
  別の置き場を持てる。既定値だけで動くので、設定しないという選択もそのまま成立する
- **`register` / `used` を Phase 2 の締めに置いた。** 説明の鮮度は「認証直後に書く」以外では保てない

## なぜ方式 A が既定で B がフォールバックか

- **A**: `open --headed --profile` でエージェントが起動、ユーザーが同じ窓で認証。1 コマンドで完結し、
  実測で `navigator.webdriver === false`
- **B**: `attach --cdp=chrome`。ユーザーに `chrome://inspect` の手動有効化と再起動を強いる。
  Chrome 136 以降の `--remote-debugging-port` 制約があるため

Google は webdriver 以外の複数シグナルで判定しており A が弾かれうる。そのときだけ B。
**検知回避フラグ（`--disable-blink-features=AutomationControlled` 等）には踏み込まない** —
このスキルの価値は「人が本物のブラウザで正規にログインする」ことであって、検知回避は別問題。

## なぜスクリプト化の指針を持つのか（`references/scripted-automation.md`）

要件 3（再ログイン不要）は**サイト側のセッションが生きている限り**しか成立しない。手作業の逐次操作なら
切れた時点でエージェントが気づいて Phase 2 に戻れるが、**スクリプト化した瞬間にその復帰路が消える**
（黙って失敗するか、ログイン画面を操作しようとする）。スクリプト側に「認証壁に当たったら通知して待つ」
契約を持たせないと、スキルの中核要件がスクリプト化のたびに壊れる。

設計上の選択:

- **`run-code --filename=` が既定で、独立した `@playwright/test` ファイルは CI 向けだけ。**
  `run-code` は `open --profile` で開いた既存セッションの**同じタブ**で動くのでログイン状態をそのまま使える。
  独立スクリプトは (a) この環境に `playwright` モジュールが無く追加インストールが要る、
  (b) 同じ `--profile` を別プロセスで掴むと「1 プロファイル = 1 インスタンス」に当たる、の 2 点で採らない
- **通知は別プロセス（`scripts/notify-user.ps1`）。**`run-code` のサンドボックスには `process` / `require` が
  無く、**スクリプトからは OS 通知を撃てない**。別プロセス化は設計の好みではなく唯一の選択肢。
  `PushNotification` は「ユーザーが端末を見ているときは送信をスキップする」仕様で、
  在席中のユーザーをブラウザに呼ぶというまさにこの用途では黙る
- **通知はベストエフォートで、失敗してもスクリプトを止めない。**トーストは環境依存（集中モード、RDP、
  実行ポリシー）。本命は会話側の依頼文で、OS 通知は気づきやすさの上乗せ。だから `notify-user.ps1` は
  トースト → ビープ → 無音と落ちながら**常に exit 0** を返す
- **ps1 だけは例外的に PowerShell スクリプト。**`profiles.mjs`（Node 単体・依存なし）と方針が違うが、
  WinRT トーストは Windows PowerShell 5.1 からしか叩けない（`pwsh` 7 では型が無い）ため Node からは出せない。
  代わりに**エントリポイントを 1 本に絞り**、bash / PowerShell どちらからも同じ 1 行で呼べる形にしてある
- **待機コード片（検知・`waitForURL`）は同梱しない。**認証ドメインのパターンはサイトごとに変わるので、
  固定スクリプトにすると必ず合わなくなる。reference 内のコード片＝毎回書き換える前提のテンプレートに留める
- **依頼文は再掲せず `handoff-protocol.md` にリンクする。**文面が 2 か所になると片方が必ず腐る

### 「認証中は打たない」との線引き

実測で分かったのは、禁止の本当の理由が「ファイルに残るから」ではなく
**「出力がエージェントの会話に入るから」**だということ（`snapshot` / `find` はファイルを書かず stdout に出す。
ファイルを書くのは `open` / `goto` / `reload`）。よって:

- `run-code` は**解禁していない**。「返り値を URL / boolean に限る」という条件付きでのみ許す、と書いている
- 待機中のセッションは CLI 側でロックされず、`snapshot` は実際に通ってしまう。
  **この禁止は仕組みでは担保できず、文章でしか守れない。**だから reference の 4 節で名指しで書いている

この線引きは誤読されやすいので、`SKILL.md`「絶対に守ること」1 と `handoff-protocol.md` の根拠文も
実測に合わせて表現を直した（禁止の範囲そのものは変えていない）。

## ファイル構成

| パス | 位置づけ |
|---|---|
| `SKILL.md` | Phase 0〜3 の手順 + 絶対に守ること。薄いルーター |
| `scripts/profiles.mjs` | 既存プロファイルの一覧・説明の登録。Node のみ、依存なし |
| `.env.example` | `BROWSER_PROFILES_ROOT` / `BROWSER_PROFILES_META`。`.env` にコピーして上書き |
| `references/handoff-protocol.md` | ユーザーへの依頼文面、待ち方、禁止コマンド一覧、資格情報を貼られたとき |
| `references/profiles.md` | 置き場・命名・1 プロファイル 1 インスタンス・秘匿情報・`state-save` を既定にしない理由 |
| `references/troubleshooting.md` | 再ログイン／多重起動／`open` が返らない／Google ブロックと B 手順／`delete-data` |
| `references/scripted-automation.md` | スクリプト化の線引き、素材の作り方、認証壁の契約、禁止事項 |
| `scripts/notify-user.ps1` | 手動ログイン待ちの OS トースト。Windows PowerShell 5.1 専用、常に exit 0 |

参照は 4 本。既存スキルの「SKILL.md は薄いルーター」方針に合わせている
（`scripted-automation.md` を SKILL.md 直下ではなく `references/` に置いたのも同じ理由。
トップレベルに 1 枚だけ置くと配置規約が崩れる）。

## 更新するとき

- **実測に基づく事実**（プロファイルパスの形、エラーメッセージ、フラグの有無）は
  `@playwright/cli` 0.1.19 / Chrome 152 / Windows 11 の実測。CLI を大きく更新したら
  `open --help` / `attach --help` を取り直し、実測し直してから本文を直す
- `.claude/rules/` には何も足していない。常時ロードされるルールに特定スキルの使い方を入れると
  全セッションのコンテキストを食うため。この判断は常用され始めたら再検討する。
  スクリプト化の指針も同じ扱いで、スキル本体（`references/scripted-automation.md`）と
  このメンテナ向け README に閉じている
- ドキュメントスナップショットの同期スクリプトは持たない。CLI 仕様の根拠資料は
  `using-playwright-cli` の `output/` にすでにある
