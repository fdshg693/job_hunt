# スキルのベストプラクティスチェックリスト

新規作成・編集時（[writing.md](writing.md)）と既存スキルの評価時（[evaluating.md](evaluating.md)）の両方から参照される共通チェックリスト。

- [ ] `name`は英数字・ハイフンのみ。動名詞形が基本
- [ ] `description`は三人称、「何をするか」+「いつ使うか」を含み、ワークフローの要約は含めない
- [ ] 自由度をタスクの性質に合わせる — 手順が一意で失敗が許されない（DB移行等）なら具体的なコマンドをそのまま指定（low freedom）。複数の正解がありうるなら方針・ヒューリスティックだけ示す（high freedom）
- [ ] 用語は統一する（例: 「抽出」と「取得」を混在させない）
- [ ] 時期依存の情報（"2025年8月以前は旧APIを使う"等）は書かない。書く場合は「旧パターン」節に隔離する
- [ ] 選択肢を並べすぎない。デフォルトを1つ示し、必要な場合だけ代替を書く
- [ ] `SKILL.md`本体は500行以内。参照ファイルが100行を超えるなら先頭に目次を置く
- [ ] スクリプトを同梱する場合はエラーハンドリングを書き込み、Claudeに丸投げしない。マジックナンバーには理由をコメントする
- [ ] 分岐・繰り返し・集計など決定論的なロジックは本文でエージェントに判断させず、スクリプトに落とし込む。目安として100行を超える複雑さになるならPythonで書く（Bashのワンライナーや本文中の擬似コードで無理に済ませない）
- [ ] 同梱スクリプトは基本的にPythonで書く。シェルスクリプト（bash/PowerShell）で環境差（Windows/Mac/Linux）を無理に吸収しようとしない
- [ ] スキル起動時に必ず実行しておきたい処理（環境情報の収集、事前チェック、既存ファイルの読み込みなど）は、エージェントの判断任せにせず`` !`command` ``形式の動的コンテキスト注入（詳細は[skills-reference.md](skills-reference.md)の「動的コンテキストの注入」節）で確実に実行させる
- [ ] frontmatterには`name`/`description`以外に`#`コメントを自由に書ける。**暗黙の前提条件**（必要な環境変数、事前インストール、初回セットアップ手順など本文の判断フローには出てこないが動作に必須な条件）、**他スキルへの依存関係**（このスキルが依存するスキル／このスキルに依存しているスキル）を書き、本文を汚さずに残す。
- [ ] 判断フローや前提条件が多く本文に収まりきらない複雑なスキルは、同階層に**メンテナ向けREADME.md**を併設する。責務を分ける: `SKILL.md`＝AIが実行時に読む判断・手順、`README.md`＝人間のメンテナが読む設計意図・全体像・セットアップ詳細。
- [ ] ファイルパスは常にフォワードスラッシュ（`scripts/foo.py`）で書く。Windows環境でもバックスラッシュは避ける
- [ ] 本文中で同梱スクリプトを実行コマンドとして書く場合、相対パス（`scripts/foo.py`）ではなく`${CLAUDE_SKILL_DIR}/scripts/foo.py`のように参照する。作業ディレクトリがスキルの置き場所と一致するとは限らないため（個人用・プロジェクト用・プラグイン用のどこにあっても正しく解決される。詳細は[skills-reference.md](skills-reference.md#利用可能な文字列置換変数一覧)）
- [ ] **Windows特有の罠**: `SKILL.md`と同じディレクトリに同梱ファイルを置く際、大文字小文字だけが違うファイル名（例: `skill.md`）は避ける。Windowsのファイルシステムは大文字小文字を区別しないため`SKILL.md`と衝突する
- [ ] MCPツールを参照する場合は`ServerName:tool_name`のように完全修飾名で書く
- [ ] ファイル名は内容が分かるものにする（`reference.md`より`skills-reference.md`、`doc1.md`は不可）
